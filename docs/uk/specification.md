# Специфікація

## Статус
Чернетка.

## Призначення
`@yuriyapostol/dyvo-vitepress-theme` — це повторно використовуваний пакет для сайтів на базі VitePress.
Він має надавати:

- повторно використовуваний шар теми поверх VitePress;
- повторно використовувані UI-компоненти і контентні фічі;
- спільні конфігураційні утиліти для SEO, метаданих і контентних домовленостей;
- стабільну поверхню інтеграції для кількох сайтів.

Пакет спочатку орієнтований на використання в `dyvoshkola.github.io`, але не повинен жорстко прив’язуватися лише до цього сайту.

## Основні цілі
1. Винести повторно використовувані кастомізації VitePress з `dyvoshkola.github.io` в окремий пакет.
2. Зберегти можливість регулярно оновлювати upstream VitePress.
3. Зберегти працездатність локальних кастомізацій, поки upstream pull request ще не змерджено.
4. Дозволити використовувати той самий пакет у кількох сайтах.
5. За замовчуванням тримати site-specific контент, навігацію і брендинг поза пакетом.

## Нецілі
- Не форкати VitePress за замовчуванням.
- Не переносити контент сайту в цей репозиторій.
- Не зашивати одну конкретну структуру сайту, якщо це явно не задокументовано як контракт фічі.
- Не виставляти внутрішні деталі реалізації як публічний API, якщо вони не призначені для довгострокової підтримки.

## Архітектурні принципи

### 1. Шарова побудова
Пакет має бути розділений на три логічні шари:

- `theme core`: layout, примітиви навігації, примітиви sidebar, спільні стилі, типи theme config;
- `features`: опційні й повторно використовувані контентні розширення, наприклад comments і news;
- `helpers`: спільні утиліти для SEO, похідних метаданих і складання конфігурації.

### 2. Публічний API на першому місці
Споживачі мають використовувати лише задокументовані exports із кореня пакета.
Внутрішні файли й каталоги можуть змінюватися без трактування цього як breaking change.

### 3. Site-specific дані лишаються зовні
Пакет може визначати схеми й утиліти для конфігурації, але реальні site-specific дані повинні лишатися в проєкті-споживачі:

- дерева навігації;
- дерева sidebar;
- URL сайту;
- брендові тексти й підписи;
- IDs зовнішніх сервісів та імена репозиторіїв;
- контентні колекції.

### 4. Сумісність з upstream важлива
Пакет має віддавати перевагу публічним API VitePress.
Імпорти з `vitepress/dist/...` допустимі лише як явний тимчасовий компроміс сумісності й мають відстежуватись як технічний борг.

## Початковий обсяг

### Theme core
Початкове `theme core` очікувано міститиме:

- кастомну обгортку `Layout`;
- local navigation;
- компоненти sidebar;
- VitePress-обгортки для спільних badge UI з `@yuriyapostol/dyvo-vue-ui`;
- базові CSS-кастомізації;
- типи конфігурації теми.

### Features
Початковий набір `features` очікувано міститиме:

- `comments`: інтеграцію коментарів на базі Giscus;
- `news`: списки, archive links, відображення метаданих і пов’язані утиліти.

Фіча `news` може залежати від задокументованого контентного контракту, включно з домовленістю про каталог на кшталт `news/**/*.md`, якщо цей контракт явно описано в документації.

Поточне рішення:

- `comments` і `news` мають бути вимкнені за замовчуванням і вмикатися явно з сайту-споживача.
- `news` поки лишається в основному пакеті. Перейменування або винесення можна переглянути пізніше.

### Helpers
Початковий обсяг утиліт очікувано міститиме:

- резервне витягування метаданих з markdown-файлів;
- побудову page identifier;
- SEO head helpers;
- locale helpers;
- helpers для складання конфігурації.

## Запропоновані публічні exports
Корінь пакета з часом має відкривати лише невеликий задокументований API:

- `theme`
- `createConfig`
- `defineThemeConfig`
- окремі повторно використовувані Vue-компоненти, лише якщо вони справді призначені для прямого використання споживачами

Призначення helper-ів:

- `defineThemeConfig` має бути типізованим helper-ом для package-specific форми `themeConfig`.
- `createConfig` має бути невеликою фабрикою для складання фінального VitePress config із package defaults і спільною конфігураційною логікою, коли така потреба реально з’явиться.

Поточне рішення:
- Поверхня exports має лишатися мінімальною, а основним API пакета будуть `theme`, `createConfig` і `defineThemeConfig`.

Можливі entry points:

- `@yuriyapostol/dyvo-vitepress-theme`
- `@yuriyapostol/dyvo-vitepress-theme/theme`
- `@yuriyapostol/dyvo-vitepress-theme/features/news`
- `@yuriyapostol/dyvo-vitepress-theme/features/comments`

Subpath exports варто додавати лише тоді, коли для них з’явиться реальна потреба.

## Модель використання
Сайт-споживач VitePress має залишатися тонким.

Очікувані обов’язки сайту-споживача:

- контентні файли;
- `.vitepress/config.*` як site assembly layer;
- site navigation і sidebar data;
- значення конфігурації для фіч;
- брендові assets і бренд-тексти, якщо їх свідомо не зроблено спільними.

Очікувані обов’язки пакета:

- реалізація повторно використовуваної теми;
- реалізація повторно використовуваних фіч;
- конфігураційні helpers і types;
- стабільні defaults там, де це доречно.

## Стратегія документації
Так, цей репозиторій може містити власний документаційний сайт на VitePress, включно з прикладами, які використовують сам пакет.
Для цього проєкту це правильний варіант.

Така документація має закривати кілька задач:

- guide з використання пакета;
- API reference;
- контракти фіч, наприклад вимоги до структури контенту для `news`;
- development notes для мейнтейнерів;
- візуальний sandbox для тестування теми й компонентів.

## Чи зробить документація пакет важчим?
Ні, якщо репозиторій структуровано правильно.

Документація не повинна потрапляти в runtime payload пакета для проєктів-споживачів.
Щоб це гарантувати:

- вихідний код пакета має жити в `src/`;
- документація має жити в `docs/`;
- docs-only залежності мають лишатися в `devDependencies`;
- вміст, що публікується як пакет, має бути обмежений через `files` у `package.json`;
- `exports` пакета мають відкривати лише entry points пакета, а не `docs/*`;
- build output пакета має бути відокремлений від build output документації.

Іншими словами, один репозиторій може одночасно містити:

- повторно використовуваний npm-пакет;
- його власний документаційний VitePress-сайт.

Але споживачі мають встановлювати лише опубліковані артефакти пакета, а не сайт документації.

## Рекомендована структура документації

```text
docs/
  index.md
  getting-started.md
  installation.md
  configuration.md
  specification.md
  components/
    theme.md
    comments.md
    news.md
```

Сайт документації може використовувати сам пакет для dogfooding.
Це бажано, якщо збірка пакета і збірка документації лишаються окремими відповідальностями.

## Обмеження пакування
Пакет має бути безпечним для використання без підтягування зайвих файлів.

Вимоги:

- `package.json` має використовувати `files` для обмеження опублікованих артефактів;
- build output пакета має йти в `dist/`;
- build output документації має йти в окрему директорію, наприклад `.vitepress/dist` всередині `docs/`, і не має публікуватися як runtime-код пакета;
- варто розглянути `peerDependencies` для `vitepress`, `vue` та пов’язаного tooling, якщо це дає чистішу інтеграцію;
- пакет має документувати сумісні діапазони версій VitePress.

## Стратегія роботи з upstream
Базова стратегія:

1. Спершу реалізовувати через кастомізацію на рівні пакета.
2. Якщо публічного API VitePress недостатньо, визначати, якої точки розширення бракує.
3. Відправляти upstream PR, якщо покращення має загальну користь.
4. Тримати тимчасовий локальний workaround, поки upstream-зміна не стане доступною.
5. Використовувати мінімальний fork або patch лише тоді, коли workaround неможливо чисто виразити в пакеті.

## Початковий план міграції
1. Створити skeleton пакета в цьому репозиторії.
2. Перенести повторно використовуваний код із `dyvoshkola.github.io/.vitepress/theme` у `src/theme`.
3. Перенести повторно використовуваний код із `dyvoshkola.github.io/.vitepress/features` у `src/features`.
4. Перенести спільні helpers у `src/shared` і `src/config`.
5. Замінити пряму site-specific реалізацію використанням пакета.
6. Стабілізувати API пакета й задокументувати feature contracts.
7. Поступово зменшувати залежність від `vitepress/dist/...`.

## Поточні рішення
- Початковий стабільний публічний API має використовувати `theme`, `createConfig` і `defineThemeConfig`.
- `comments` і `news` мають бути opt-in.
- `news` має поки лишатися всередині основного пакета.
- Пакет спочатку має використовуватись локально через `file:` dependency.
- Після стабілізації локальної інтеграції сайт-споживач має перейти на git dependency з GitHub, зафіксовану на конкретній версії, наприклад через тег або commit SHA.
- Пакет має офіційно підтримувати ту саму мінорну гілку VitePress, що й сайт-споживач, а зараз це `^1.6.4`.

## Безпосередній наступний крок
Використовувати цю специфікацію як джерело істини для scaffolding пакета і для винесення коду з `dyvoshkola.github.io` у `dyvo-vitepress-theme`.
